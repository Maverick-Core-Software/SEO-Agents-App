# Research: Grizzly Marketing Control — weekly operator workflow, IA, screens, and first read-only slice

## Summary
The current marketing surface in MCC is a single React page (`src/SEOApprovalPage.jsx`) backed by a Supabase-driven bridge (`SEO-Agents-App/scripts/mav-bridge.mjs`) that already implements the full create→approve→publish→verify→recover loop as discrete states and endpoints — but mixes them into one scroll, shows no performance data, and gates GBP posting on an unconfigured adapter. ## Analysis (inference / design)

**Rhythm → workflow mapping.** The operator's week maps 1:1 onto observed states: **Create** (`+ Generate Schedule` → `/seo/facebook/new-schedule`; weekly crew run → `seo_runs` + `weekly_posts` at `pending_approval`; website tasks from execution queue) → **Review** (content detail; Day-1 video prompt gate `awaiting_prompt`) → **Approve** (`approve` cascades run + posts → bridge poll → `executing`/`posting`; per-item `dismiss` for skip) → **Publish** (FB `facebook-poster --schedule-all --time 09:00`: Day 1 posted, Days 2–7 native-scheduled; GBP `scheduled` via worker/API; website tasks auto-executed by priority) → **Verify** (daily Graph reconcile, TTL stuck-reset, `needs_verification` for GBP, `postHealth` red/green chips) → **Learn** (engagement report, boost ledger, baselines — all currently invisible to the UI) → **Recover** (`retry` with scope, `dismiss`, `clear-fault ack`, `/ops/clear-lock`; one-time Slack+email alerts).

**Information architecture — 7 primary screens + recovery zone** (each grounded in payloads above):

1. **Today / This Week** (default). Week-anchored grid (Mon–Sun × Facebook/Google Business, from `/seo/posts/week` payload `{week_start, week_end, run_status, facebook[], gbp[]}`) with POST TODAY / OVERDUE / CHECK chips and health chips; Today strip: pending count, alerts/faults, adapter readiness dots, next action (`workflow_status.json.next_action`). Fields per row: day, date, service/hook, status, media_status, posted_at, error, priority.
2. **Content Calendar.** 2–4 week grid across Facebook + GBP + blog with status colors (pending_approval/approved/scheduled/scheduled_native/posted/needs_verification/error/skipped) from `weekly_posts`; click-through to Content Detail; per-week summary counts.
3. **Approval Inbox.** Grouped queue (`seo_run` / `weekly_post` / `website_task`) from `/seo/actions`; fields: type, title, priority (P1..P3), risk, confidence, due date, assigned agent, media status, error. Bulk approve + per-item Approve / Skip. Inherits the current page's rule: website tasks collapsed, weekly posts absorbed into the calendar once approved.
4. **Content Detail** (drawer/page). Full copy fields from the action model: headline, body, caption, hook, CTA, hashtags, photo_file (with `[CONFIRM]` flag), service, topic, trend_tie (the research rationale — key trust input), day/date, platform, plus approval scaffolding: steps, dependencies, verification checklist, rollback, preconditions, acceptance criteria, confidence, idempotency key, run history (posted_at, platform_post_id, media_status, error). Actions: Approve / Skip / Run / Retry / Edit note.
5. **Website Tasks.** Priority-ordered list from `website_tasks` + adapter capabilities; fields: title, priority, status, error, capability type, site section, preview path (`outputs/website_preview/`), auto-exec flag (`MAV_WEBSITE_AUTO_EXEC`), per-task Approve/Skip/Retry.
6. **Performance.** What exists but is unsurfaced: Facebook engagement report, boost ledger, weekly baselines, review count vs competitor (154 vs W3's ~1,500 in the schedule doc). Week-over-week trend needs a structured store (today only markdown) — flag as build gap.
7. **Operations.** Adapter readiness (from `/seo/actions` adapters + `adapter-status --json`), run history + `run_logs`, fault ack state, `state/fault-acks.json`, `run_health.json` failed-phase flags, `/ops/clear-lock`, bridge `/health`, task event log (Task Activity).

**Recovery journey.** A first-class "Needs recovery" zone (today it's a mid-page section of failed cards): aggregates `failed|stuck` buckets (`status_detail === 'stuck'`, `isStuck` thresholds per type) across runs/posts/tasks; per item: reason (error text / "In process longer than N limit" / "Stuck in posting state >30min — auto-reset"), then Retry (with scope selector for runs: action / FB-only / all), Skip (dismiss), or Ack (clear-fault, suppresses push + dashboard fault for 7 days). Terminal states `skipped|rejected|dismissed|cancelled` map to "incomplete", not "partial" (`seo-run-status.mjs`). The 2026-07-31 missed-run handoff is the historical justification for surfacing this zone at the top.

**First read-only slice (no writes).** Reads only: file outputs (`workflow_status.json`, `action_queue.json`, `gbp_posting_schedule.md`, `facebook_posting_schedule.md`, `run_health.json`, report markdowns, `state/fault-acks.json`, `knowledge/baselines/`, `outputs/action_runs/`) plus GET endpoints (`/seo/status`, `/seo/actions`, `/seo/posts/week`, `/seo/facebook/pending-prompt`, `/tasks/log`, `/health`). Must show, in order: (1) workflow state badge + phase + next action; (2) Today/This Week grid with health chips; (3) approval queue with priorities/risk/confidence; (4) website task list with adapter readiness; (5) alerts/faults strip; (6) content detail preview; (7) performance report links. Mutating buttons rendered disabled with "write action — read-only slice" tooltip; zero POST calls. Every screen is implementable against existing GETs and files — no backend work needed for the slice.
